# Reproducibility Guide

## Reproduction status

**Status for v0.8.0: the repository provides a reproducible execution framework, but it does not claim that the historical published/notebook results have already been independently reproduced with the refactored pipeline.**

This distinction is intentional. A clean GitHub repository should not label a result as "reproduced" merely because code or a notebook is present.

### What is available now

- Explicit YAML experiment configurations under `configs/`.
- Seed handling through `koa_severity.reproducibility`.
- Recorded run metadata under `results/runs/`.
- Shared evaluation/metric utilities.
- Checkpoint validation helpers.
- 9 curated notebooks with portable paths and no saved outputs.
- Original notebooks preserved under `archive/raw_notebooks/`.
- Automated tests and repository validation.

### What is not claimed

The repository does **not** claim that every historical metric, figure, checkpoint, or notebook result has been regenerated by the current code. Historical results remain tied to their original research artifacts until a target experiment is explicitly rerun and compared.

## 1. Environment

Create an isolated Python environment and install the repository:

```bash
python -m venv .venv
python -m pip install --upgrade pip
pip install -e ".[dev]"
```

For GPU experiments, use a PyTorch build compatible with the target CUDA/CPU environment. Exact hardware/software differences can affect training results.

## 2. Dataset

The dataset is intentionally external to Git. Set:

```text
KOA_DATASET_PATH=/path/to/dataset
```

Do not commit datasets, credentials, or downloaded archives.

Before claiming a reproduction, record the dataset identity/version, directory layout, class mapping, and train/validation/test split used by the target experiment.

## 3. Randomness and determinism

Use `koa_severity.reproducibility.seed_everything()` for experiments that require a recorded seed.

Deterministic settings can reduce performance and do not guarantee bit-for-bit equality across different hardware, CUDA, PyTorch, torchvision, or driver versions.

## 4. Configuration and run provenance

Each current pipeline experiment should start from a versioned YAML configuration, for example:

```bash
python scripts/run_experiment.py --config configs/resnet18_baseline.yaml
```

The run metadata records the configuration used for that run. Keep the resulting `results/runs/<run-name>/run.json` with any experiment report.

## 5. Checkpoints

Model checkpoints are local artifacts and are ignored by Git by default. Checkpoint helpers validate expected files and state dictionaries where applicable.

If a result depends on a specific checkpoint, record its provenance (filename, source, date/version, and checksum when available) rather than silently replacing it with another weight file.

## 6. Evaluation

Use the shared metrics implementation where possible. For ordinal threshold probabilities, `strict=True` validates the expected non-increasing threshold structure instead of silently repairing invalid predictions.

When comparing against a historical result, use the same dataset split, preprocessing, class mapping, evaluation definition, and checkpoint whenever those details are known.

## 7. What counts as a completed reproduction?

A reproduction should document at least:

- target experiment/notebook;
- dataset identity and split;
- environment/package versions;
- configuration and random seed;
- model/checkpoint provenance;
- preprocessing and evaluation protocol;
- generated metrics/figures;
- comparison with the historical target result;
- any deviations or unresolved differences.

Until these steps are completed, use language such as **"reproduction framework"**, **"curated workflow"**, or **"historical result"**, rather than claiming successful reproduction.
